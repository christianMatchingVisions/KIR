the Matching Visions Content Engine live for KIR (`kasinotilmanrekisteroitymista`).

Everything shipped is **strictly additive and gated** — until you run the steps
below, the engine pipeline is byte-identical for OCL and KIR builds render
exactly as today (pure-scraped casinos, news-only `/uutiset/`). Do the steps
**in order**. Where a step is destructive or shared, it says so.

## (a) Review + apply the Drizzle migration on the shared Neon DB

The only schema change is **one new table** `casino_review_data` — no `ALTER` on
any existing table, so it cannot affect OCL.

**Migration file:** `content enigne/drizzle/migrations/0009_daily_tusk.sql`
(registered in `drizzle/migrations/meta/_journal.json` as idx 9).

1. Review the SQL (it should only `CREATE TABLE "casino_review_data"`, its FKs to
   `articles`/`sites`, and 5 indexes):

   ```bash

   cat drizzle/migrations/0009_daily_tusk.sql
   ```

2. Apply it to the **shared production Neon** DB. Drizzle tracks applied
   migrations in `__drizzle_migrations`, so this applies **only** 0009 (0000–0008
   are already applied for OCL):

   ```bash
   # Point at the PROD pooled Neon URL. drizzle.config.ts reads DATABASE_URL.
   DATABASE_URL="<prod pooled neon url>" pnpm drizzle-kit migrate
   ```

   - `pnpm db:migrate` is the same command (`drizzle-kit migrate`) if your
     `.env.local`/`.env.production` already holds the prod `DATABASE_URL`.
   - Do **not** use `drizzle-kit push` (it diffs live schema and can drift).

3. Verify the table exists and is empty:

   ```bash
   psql "<prod pooled neon url>" -c "\d casino_review_data"
   psql "<prod pooled neon url>" -c "select count(*) from casino_review_data;"  # 0
   ```

The table is **inert** until the engine writes to it (step d) — no reviews are
generated by creating the table.

## (d) Run the review pilot (~15 slugs), then process the jobs

The pilot **only enqueues** review-generation jobs; it does **not** run the
worker. Generation happens when the sweeper/worker processes the queue.

1. Enqueue the pilot (default limit 15, language fi, quality premium). Dry-run
   first to see exactly what would be enqueued:

   ```bash
   cd "C:/Users/chrni/Desktop/matching visions projects/content enigne"

   # DRY RUN — prints the 15 slugs + topics, writes nothing:
   node --env-file=.env.local scripts/enqueue-reviews-kir.mjs \
     --slugs scripts/data/kir-casino-slugs.txt --limit 15 --dry

   # REAL — inserts 15 'queued' jobs (idempotent: skips slugs that already
   # have a non-terminal review job for this site):
   node --env-file=.env.local scripts/enqueue-reviews-kir.mjs \
     --slugs scripts/data/kir-casino-slugs.txt --limit 15
   ```

   Each job carries the gate fields on its request:
   `article_type:"review"`, `structured_data_type:"casino_review"`,
   `review_target:{ casino_slug, name }`. The slug equals the KIR
   `/casino/<slug>/` join key. The default slug list is the 305 KIR casino
   fragment names; `--limit 15` takes the first 15. (To control which 15, edit
   `scripts/data/kir-casino-slugs.txt` or pass your own `--slugs` file. To seed
   the engine extraction with scraped facts, add `known_facts` to the
   `review_target` in `buildRequest`.)

2. Process the jobs. In production Railway runs the sweeper on its in-process
   cron, so jobs drain automatically. To drive them now (or locally):

   ```bash
   # Kick the prod sweeper (drives queued jobs through the stages):
   curl -s -H "authorization: Bearer $CRON_SECRET" \
     "https://<engine-domain>/api/internal/cron/sweeper"

   # …or locally, drive jobs to completion:
   APP_URL=http://localhost:3000 node --env-file=.env.local scripts/drive-job.mjs
   ```

   For each review job the pipeline runs the normal stages
   (validate→research→…→compliance). On the compliance **pass**, the gated
   `extract-review` step runs `generateObjectRouted(zCasinoReviewExtraction)`,
   merges the scraped `known_facts` (FILL-GAPS + OVERRIDE), runs the deterministic
   review gates (cite license; no first-hand/"testattu" claims; rating consistent
   with sub-ratings), and **upserts** a `casino_review_data` row:
   - all gates pass → `status='delivered'` → ships in `GET /v1/reviews`;
   - any gate fails → `status='needs_review'` → withheld from the feed (work it
     in the dashboard, then re-run the job to re-extract).

3. Confirm delivery:

   ```bash
   curl -s -H "authorization: Bearer $CE_API_KEY" \
     "https://<engine-domain>/v1/reviews?status=delivered" | python -m json.tool | head -40
   ```

   When the pilot looks good, **ramp** by re-running the enqueue with a larger
   `--limit` (e.g. `--limit 50`, then the full 305). Idempotency means
   already-done slugs are skipped.

## Rollback (everything is additive — no data loss)

To disable, in increasing order of thoroughness:

1. **Stop new reviews (fastest):** re-run the enable script without `review`:

   ```bash
   node --env-file=.env.local scripts/enable-kir-streams.mjs \
     --site kasinotilmanrekisteroitymista --types news,guide
   ```

   New review jobs stop being planned. (Drop `guide` too → `--types news` — to
   also stop new guides; existing pages persist until the next KIR build.)

2. **Hide delivered reviews from KIR without touching the engine:** unset
   `CE_API_URL`/`CE_API_KEY` in Vercel (or just for `/reviews` by parking the
   feed) and redeploy — KIR's loader no-ops to an empty Map and every casino
   renders pure-scraped again. The `/oppaat/` hub falls back to scraped guides.

3. **Stop delivering at the source:** flip rows to non-delivered (the feed only
   ships `status='delivered'`):

   ```sql
   UPDATE casino_review_data SET status = 'needs_review'
   WHERE site_id = (SELECT id FROM sites
                    WHERE slug = 'kasinotilmanrekisteroitymista');
   ```

4. **Full removal (rarely needed):** the table + endpoint are inert when empty
   and unreferenced. Drop the table only if you also revert the schema/code:

   ```sql
   DROP TABLE IF EXISTS casino_review_data;
   ```

The `extract-review` stage is invoked **only** behind the
`isCasinoReviewJob(job)` gate (`article_type='review'` AND
`structured_data_type='casino_review'` AND a valid `review_target`). With no
review jobs enqueued the gate is always closed, so the compliance stage never
calls it and the pipeline is byte-identical to today — including for OCL.
